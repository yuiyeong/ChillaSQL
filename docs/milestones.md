# ChillaSQL 마일스톤

[기획서](spec.md) 8장의 4단계를 11개 마일스톤(M0~M10)으로 나눈다. 마일스톤 하나는 끝났을 때 실제로 띄워서 확인할 수 있는 결과를 남긴다. 상태와 기록은 [진행상황](progress.md)에 둔다.

## 진행 방법

1. **시작**: `docs/plans/M<n>-<name>.md`에 그 마일스톤의 계획을 쓴다. task 단위로 나누고, 각 task는 test → 구현 → 확인 → commit 순서의 체크박스를 가진다. 진행상황의 상태를 `계획 중`으로 바꾼다.
2. **계획 확정**: 아래 "먼저 확인할 것"을 계획의 첫 task로 넣어 먼저 해결한다. 상태를 `진행 중`으로 바꾼다.
3. **작업**: task를 끝낼 때마다 계획 파일의 체크박스를 체크하고 commit한다.
4. **세션 끝**: 진행상황의 "지금"과 작업 로그를 갱신한다. 다음 세션은 "지금"만 읽고 이어간다.
5. **완료**: 완료 기준을 실제로 확인하고 결과를 작업 로그에 남긴 뒤 상태를 `완료`로 바꾼다. 단계의 마지막 마일스톤이면 기획서 8장대로 며칠 실제로 써 보고 다음 단계로 넘어간다.

계획은 마일스톤을 시작할 때 쓴다. 뒤쪽 마일스톤은 앞에서 만든 코드에 맞춰야 하므로 미리 써 두지 않는다.

기획서와 다르게 정하거나 기획서에 없는 것을 정하면 진행상황의 결정 기록에 남기고, 기획서도 함께 고친다.

M4부터 화면 모양은 [디자인](design/README.md)의 캔버스 사본을 따른다. 다르게 만들어야 하면 결정 기록에 남긴다.

## 순서

```
1단계  M0 셋업 → M1 접속·세션 코어 → M2 쿼리 실행 코어 → M3 프로젝트·에디터 화면 → M4 결과 표
2단계  M5 터널 → M6 트랜잭션과 안전장치
3단계  M7 스키마 트리와 자동완성 → M8 에디터·실행 편의
4단계  M9 쿼리 도구 → M10 결과 표 확장
```

M5는 M1에만 의존하므로 앞당길 수 있다. 나머지는 순서대로 진행한다.

## 1단계: 뼈대

### M0. 셋업

- **목표**: 빈 Tauri 앱이 뜨고, Rust와 화면 양쪽 test가 돌아가는 상태
- **범위**: Tauri 2 + React + TypeScript + Vite + Tailwind + Zustand 초기 구성, Rust crate 구조(Tauri command 층과 DB 코어 분리), cargo test와 vitest 설정, test용 로컬 PostgreSQL(docker compose, PostgreSQL 18), 100만 행 test 데이터 생성 스크립트
- **완료 기준**: `pnpm tauri dev`로 창이 뜸. `cargo test`, `pnpm test`가 통과. 스크립트 하나로 test DB가 뜨고 100만 행 테이블이 생김
- **먼저 확인할 것**: `pg_query` crate(libpg_query를 C로 빌드)가 Tauri 빌드 안에서 컴파일되는지

### M1. 접속·세션 코어 (Rust)

- **목표**: Rust 쪽에서 프로젝트를 열고 저장된 접속으로 세션을 열고 닫을 수 있음
- **범위**: `chilla.toml` 읽기(기획서 5장), 접속 정보 형식(4.1), SSL 모드와 rustls 인증서 검증(`require`, `verify-full`), 키체인 비밀번호 저장과 조회(7장), 접속 테스트, 탭 = 세션 구조(탭마다 전용 연결 1개, 4.3), 세션 actor와 Tauri command 경계, 비밀번호를 화면으로 넘기지 않는 구조, 로그에서 접속 문자열과 비밀번호 제외
- **완료 기준**: integration test가 로컬 DB에 접속, 세션 2개를 따로 열고 닫음. `verify-full`로 인증서가 틀린 서버를 거부함. 설정 파일에 password 항목이 있으면 거부함
- **먼저 확인할 것**:
  - 결과를 500행씩 나눠 받는 방법. portal(`query_portal`)은 트랜잭션 안에서만 살아 있고, `RowStream`을 덜 읽고 두면 연결이 막힌다. 어느 쪽이든 세션 구조가 달라지므로 여기서 정한다
  - 트랜잭션 상태(열림, 실패) 감지 방법. tokio-postgres가 ReadyForQuery의 상태 값을 공개하는지 확인하고, 없으면 대안(SQL 파서로 BEGIN/COMMIT 추적 등)을 정한다. M6이 이 위에 올라간다
  - 서명하지 않은 로컬 빌드가 다시 빌드될 때마다 키체인 접근 확인 창을 띄우는지

### M2. 쿼리 실행 코어 (Rust)

- **목표**: 세션에서 SQL을 실행하고 결과를 500행씩 화면으로 보낼 수 있음
- **범위**: pg_query로 문장 나누기와 문장 위치 반환(4.5), 커서 문장과 선택 영역 실행, 결과를 500행 단위로 Tauri Channel로 전송, 스크롤 요청 시 이어서 가져오기, 같은 탭에서 다음 쿼리를 실행하면 남은 결과 버리기, 실행 정보(소요 시간, 영향받은 행 수), 쿼리 취소(별도 연결로 cancel 요청), 탭당 10만 행 보관 상한과 버려진 구간 표시용 정보(4.6)
- **완료 기준**: test로 `$$` 블록, 문자열, 주석 안의 `;`를 경계로 보지 않음을 확인. 100만 행 쿼리의 첫 500행이 DB 응답 후 0.1초 안에 Channel에 도착. 10초짜리 `pg_sleep` 쿼리가 취소 후 1초 안에 끝남
- **먼저 확인할 것**: 500행 묶음을 Channel로 보낼 때의 직렬화 형식과 크기(JSON으로 충분한지)

### M3. 프로젝트·에디터 화면

- **목표**: 앱에서 프로젝트를 열고, 접속을 고르고, SQL을 써서 실행할 수 있음
- **범위**: 프로젝트 디렉토리 열기와 SQL 파일 목록, 접속 목록과 접속 추가/수정 화면(비밀번호 입력은 키체인으로 바로 저장), 접속 테스트 버튼, CodeMirror 6 에디터와 PostgreSQL Highlighting(`::`, `$$`, JSONB 연산자, 4.4), SQL 파일 탭과 `.sql` 저장, 커서 문장과 선택 영역 실행, 취소 버튼, 실행 정보 표시, 기본 단축키(Cmd+Enter 등 DataGrip macOS 키맵, 4.10). 결과는 임시 표로만 보여 준다
- **완료 기준**: 앱 시작부터 프로젝트 화면까지 1초 이내. 로컬 DB에 접속해 쿼리를 Cmd+Enter로 실행하고 취소할 수 있음
- **먼저 확인할 것**:
  - 커서 위치에서 실행할 문장을 고를 때 M2의 문장 위치 정보를 쓸지, 화면 쪽에서 따로 판별할지
  - `tauri.conf.json`의 CSP를 켠다(지금은 `null`). Vite HMR과 CodeMirror가 넣는 style이 막히지 않는 정책을 정한다 → 정함: `default-src 'self'; connect-src ipc: http://ipc.localhost; img-src 'self' data:; style-src 'self' 'unsafe-inline'`. 빌드된 앱에만 적용(desktop `tauri dev`에는 CSP가 붙지 않음)
  - `pnpm tauri dev` 빌드마다 키체인 확인 창이 뜬다(M1에서 확인). dev 빌드를 고정된 self-signed code signing identity로 서명할지 정한다 → 정함: cargo runner script가 이 Mac에 이미 있는 identity로 서명(새로 만들지 않음). 다시 빌드해도 확인 창이 뜨지 않음

### M4. 결과 표

- **목표**: 1단계 완료 기준 달성
- **범위**: TanStack Table + TanStack Virtual 결과 표, 가상 스크롤과 스크롤 시 이어서 가져오기, 보관 상한을 넘어 버려진 구간에 "다시 실행해야 볼 수 있음" 표시, 컬럼 너비 조절, 셀과 행 복사, 화면 문구를 영어 dictionary(`en`)로 옮김(M3의 한국어 문구와 macOS menu 포함), D2Coding을 앱에 넣고 에디터와 결과 표에 적용, 캔버스 디자인 적용(시각 token을 Tailwind theme으로: 색, 글자 크기 17/15/13/12, control 높이 28px. sidebar의 접속 영역과 파일/스키마/기록 탭 틀, title bar를 겸하는 탭 줄과 창 상단 접속 bar, toolbar의 접속 chip과 접속 고르기 menu, 너비를 고정한 split 실행 버튼(Run statement / Run selection, 파일 전체 실행 menu), 결과 panel header, 이어서 가져오는 중과 결과의 끝 표시, 빈 상태의 단축키 안내, 접속이 없는 탭, status bar), 행 복사 뒤 알림
- **완료 기준 (1단계)**: 로컬 DB에서 100만 행 결과를 끊김 없이 스크롤. 못 맞추면 기획서 2장대로 canvas 기반 그리드로 교체를 검토한다
- **먼저 확인할 것**:
  - release 빌드(`pnpm tauri build`)를 dev 빌드와 같은 identity로 서명할지(`bundle.macOS.signingIdentity`). 서명이 다르면 키체인이 다른 앱으로 본다
  - M3의 임시 결과 표는 첫 batch만 보여 주고 `fetch_more`를 부르지 않는다. 이를 대신할 때 `runReducer`가 이미 `retainedFrom`보다 앞의 행을 버리는 것과 맞춘다

## 2단계: 터널과 트랜잭션

### M5. 터널

- **목표**: 터미널 없이 터널이 필요한 DB에 접속
- **범위**: 터널 명령을 자식 프로세스로 실행, host:port가 열릴 때까지 대기(기본 20초, 접속별 변경), 실패 시 명령의 오류 출력 표시, 포트가 이미 열려 있으면 실행하지 않고 "앱이 띄우지 않은 터널" 표시, 같은 접속의 탭끼리 터널 공유(참조 수 관리), 마지막 세션이 끊기면 터널 종료, 프로세스 종료 감지와 재실행(연속 3회 실패 시 중단), 재연결 후 세션 상태 초기화 알림, 앱 종료 시 앱이 띄운 터널 모두 종료(4.2), 접속 테스트에 터널 포함(4.1), 접속 sheet에 `tunnel`과 `tunnel_timeout` 칸, 테스트 실패 시 명령의 오류 출력 표시, 탭과 toolbar의 터널 상태(시작 중, 실패, 재연결 n/3, 앱이 띄우지 않은 터널)
- **완료 기준**: 터미널 없이 Railway staging에 접속. 터널 프로세스를 강제로 죽이면 재연결되고 알림이 뜸. 앱을 종료하면 터널 프로세스가 남지 않음
- **먼저 확인할 것**:
  - 접속 sheet에 둘 key 이름(캔버스는 `tunnel_timeout`으로 제안)
  - Finder에서 띄운 앱은 shell의 PATH를 받지 못해 `railway`를 못 찾는다. 사용자 login shell(`$SHELL -lc`)로 실행할지 정한다
  - shell을 거쳐 실행하면 손자 프로세스가 생기므로 process group 단위로 종료하는 방법
  - `establish`와 `PgCancel`이 stream을 여는 분기를 따로 갖고 있다. 터널로 여는 방법이 바뀔 때 하나로 묶는다

### M6. 트랜잭션과 안전장치

- **목표**: 2단계 완료 기준 달성. 이후 운영 DB 접속 가능
- **범위**: Auto/Manual 전환(탭 단위), Commit과 Rollback 버튼, 열린 트랜잭션 표시(직접 BEGIN한 경우 포함), 트랜잭션이 열린 채 탭 닫기/앱 종료/Auto 전환/탭의 접속 바꾸기 시 확인(앱 종료는 모두 Rollback 또는 취소), 실패 상태 표시와 Rollback 안내(4.3), 트랜잭션 중 터널이 끊기면 유실 알림, 접속별 색상(창 상단 bar, 탭, toolbar, 4.1), 위험 쿼리 확인(WHERE 없는 UPDATE/DELETE, DROP, TRUNCATE를 pg_query로 판별, 4.8), 받다 만 결과 10분 후 자동 닫기(4.6), 탭과 toolbar에 트랜잭션 경과 시간과 문장 수 표시, 위험 쿼리 확인 문구를 Manual(되돌릴 수 있음)과 Auto(되돌릴 수 없음)로 나눔, 접속 sheet의 `color` 칸
- **완료 기준 (2단계)**: 터미널 없이 Railway staging에 접속해 Manual 트랜잭션을 Commit, Rollback
- **먼저 확인할 것**:
  - M1에서 정한 트랜잭션 상태 감지 방법을 쓴다
  - Commit Opt+Shift+Cmd+K, Rollback Opt+Shift+Cmd+Z가 DataGrip macOS 기본 키맵과 같은지(4.10)
  - 접속의 연결 대상을 고쳐 저장하거나 프로젝트를 바꾸면 그 접속의 세션을 묻지 않고 닫는다(M3). 열린 트랜잭션이 생기면 탭을 닫을 때와 같은 확인이 필요하다

## 3단계: 매일 쓰는 편의

### M7. 스키마 트리와 자동완성

- **목표**: 스키마를 탐색하고 자동완성으로 쿼리를 쓸 수 있음
- **범위**: 스키마 트리(스키마, 테이블, 뷰, 컬럼, 인덱스, 제약조건), 펼친 항목만 조회, 수동 새로고침, 테이블 더블클릭 시 앞부분 행 조회(4.7), 트리 항목 menu와 이름 복사, 스키마는 활성 탭의 접속을 따름, 접속 후 스키마 정보를 뒤에서 불러와 메모리에 보관, 자동완성(키워드, 스키마, 테이블, 컬럼, 함수, 테이블 별칭 인식, 4.4)
- **완료 기준**: 자동완성이 0.05초 이내에 뜸. 새로고침하면 새 테이블이 트리와 자동완성 양쪽에 나타남
- **먼저 확인할 것**: 별칭 인식을 lang-sql 기본 기능으로 할 수 있는지, 따로 만들어야 하는지

### M8. 에디터·실행 편의

- **목표**: 3단계 완료 기준 달성
- **범위**: Formatting(sql-formatter, 선택 영역 또는 파일 전체, Opt+Cmd+L), DB가 알려준 오류 위치 밑줄, 파일 전체 실행과 문장별 결과 탭(오류 난 문장에서 멈춤), 타입별 표시(JSONB 펼쳐보기, timestamptz, 배열, NULL과 빈 문자열 구분, 긴 값 줄임), 읽기 전용 접속(4.8), 접속별 타임아웃(4.5), 저장하지 않은 탭 내용을 SQLite에 보관하고 재시작 후 복원, 최근 프로젝트 목록과 프로젝트 바꾸기 menu(Cmd+O), 읽기 전용 접속에서는 위험 쿼리 확인을 건너뜀(4.8), 결과 column header의 type 표시, 셀을 고르면 옆 panel에 전체 값(Shift+Enter), 에디터에서 실행될 문장 범위 강조(배경과 왼쪽 선), 접속 sheet의 `read_only`와 `statement_timeout` 칸과 Advanced 접기, 전역 설정 파일 `~/.config/chilla/config.toml`(5장), 한국어 dictionary(`ko`)와 `language` 설정, 에디터 글꼴과 크기 설정
- **완료 기준 (3단계)**: 하루 업무를 DataGrip 없이 처리
- **먼저 확인할 것**:
  - simple query protocol은 컬럼의 type OID를 주지 않는다(M2 결정). 타입별 표시에 필요한 type을 `TxTap`이 RowDescription을 읽어 얻을지, `prepare`로 Describe할지 정한다
  - 실행될 문장 범위 강조를 커서가 움직일 때마다 계산해도 1만 줄 파일에서 입력이 늦어지지 않는지(`split_statements`는 1만 줄에 약 40ms)
  - 접속 sheet에 둘 key 이름(캔버스는 `read_only`, `statement_timeout`으로 제안)
  - M3는 마지막 프로젝트를 `localStorage`에 두고, 앱을 끝낼 때 저장하지 않은 탭을 묻지 않는다. 최근 프로젝트 목록과 자동 보관이 이 둘을 대신한다

## 4단계: 나머지

### M9. 쿼리 도구

- **목표**: 쿼리 기록, 파라미터, 실행 계획, DDL 보기
- **범위**: 쿼리 기록 자동 저장과 검색, 에디터로 다시 불러오기(4.9), `:id` 파라미터 입력(`::` 캐스팅과 구분, 4.5), EXPLAIN ANALYZE 결과 보기(tree, 가장 오래 걸린 노드 강조, 원문 보기), 테이블 생성문 보기(복사, 새 탭에 열기, 4.7)
- **완료 기준**: 어제 실행한 쿼리를 검색해 다시 실행. `:id`가 있는 쿼리를 값을 넣어 실행
- **먼저 확인할 것**:
  - PostgreSQL에는 생성문을 돌려주는 함수가 없으므로 DDL을 카탈로그로 조립할 범위(컬럼, 제약조건, 인덱스, 코멘트 등)
  - `pg_query`의 parser는 `:id`를 문법 오류로 본다(M2에서 확인). 파라미터는 scanner token으로 `::`와 구분한다

### M10. 결과 표 확장

- **목표**: 4장의 모든 기능 동작
- **범위**: 셀 편집(PK가 있는 단일 테이블 결과에서 UPDATE로 반영, 4.6), 화면 내 정렬(일부만 받은 결과면 표시), CSV와 JSON 내보내기, 전역 설정 파일로 단축키 변경(4.10)
- **완료 기준 (4단계)**: 기획서 4장의 모든 기능 동작
- **먼저 확인할 것**: 결과가 단일 테이블에서 왔는지 판별하는 방법(RowDescription의 테이블 OID와 컬럼 번호)
